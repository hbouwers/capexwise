# ADR-0005: Identifiers, money, and dates

**Status:** Proposed — accepted on merge of the PR that adds it
**Date:** 2026-09-08
**Decided by:** Holden

## Context

Three conventions that cost one line each before there is data and a migration afterwards. They
are grouped into one ADR because they share that shape, not because they are otherwise related.

Each has a specific failure this project cares about. Sequential identifiers on a multi-tenant
product leak portfolio size to anyone who can read a URL. Money in a float is wrong by cents, and
this application puts money on a tax page where being wrong is worse than being absent. And dates
here are genuinely heterogeneous — a furnace has an install *year* that is usually a guess, a
gutter cleaning has a due *date* with no clock time, and a rent payment has a moment it was
received — so one column type cannot serve all three without lying about at least two of them.

## Decision

### Identifiers: UUIDv7, generated by Postgres

Primary keys are `uuid`, generated by the database default using Postgres's built-in `uuidv7()`.

PostgreSQL 18 (released late September 2025) added `uuidv7()` natively, conforming to RFC 9562,
along with `uuid_extract_timestamp()`. That removes the reason people reach for ULID — no
application library, no text or `bytea` column standing in for a native type, no second
implementation to keep consistent between the app, the seed script and a manual `INSERT`.

**This pins Postgres to 18 or newer, and that constraint belongs in #33** when the managed instance
is provisioned. It is the real cost of this decision and the only one.

Generation is a **column default in the database**, so every row gets a well-formed id regardless
of whether it arrived through the application, a migration, a backfill or the demo seed (#34). The
application can still supply an id when it needs one before insert.

One honest trade: a UUIDv7 embeds its creation timestamp, so it leaks *when* a row was created.
That is a real disclosure and it is accepted deliberately, because the alternative it replaces
leaks *how many* rows exist — which for this product is portfolio size, and is the thing the hard
rule in `CLAUDE.md` exists to prevent.

### Money: integer cents, in `bigint`

One `Money` type and one formatter, used everywhere — the forecast, the tax planner, rent periods,
replacement costs. Never a float. Never a `numeric` round-tripped through JavaScript, which is the
subtler failure: the driver hands back a string to preserve precision, and the first arithmetic
operation quietly turns it into a float anyway.

Two rules that follow, and that are easy to get wrong later:

- **Round at the point of display, never in storage, and never accumulate rounded values.** A
  ten-year forecast that rounds each year and sums the rounded figures does not match the same
  forecast summed and then rounded.
- **Allocations must sum to the total.** ADR-0003 and #48 put shared capital items on the building,
  and F4 splits their basis across units. Naive division loses cents: a $10,000.01 roof across two
  units is not two halves. Use a largest-remainder split so the parts add up to the whole, because
  a tax page whose lines do not sum to its total is exactly the traceability failure the PRD is
  most worried about.

### Dates: four kinds, four column types

| What | Type | Why |
|---|---|---|
| Capital item install year | `integer` year, plus a nullable `install_date` | The common case is a guess from the building's build year. A year is what is actually known |
| Task due date | `date` | "Clean the gutters on the 14th" has no clock time and no timezone |
| Rent period | `date` pinned to the first of the month, with a check constraint | Sorts and ranges natively, unlike a (year, month) pair |
| Anything that happened | `timestamptz`, stored UTC | `created_at`, `updated_at`, `received_on` |

**Estimated versus audited is a `confidence` enum plus a nullable precise date — never a magic date
value.** `install_year = 2009, confidence = 'estimated', install_date = null` says exactly what is
known. Encoding the same thing as `2009-01-01` and inferring "January the first means we guessed"
is a convention that survives until the first furnace genuinely installed on New Year's Day, and
that fails silently rather than loudly.

**Timezone rule: store UTC, render in the building's local zone.** Not the viewer's. The owner is
in Bloomington and the buildings are in Indianapolis; they share a zone today, which is an accident
of this portfolio and not a rule to build on. `buildings.timezone` holds an IANA name, and "due
today" means today where the building is, because that is where the gutters are.

## Alternatives considered

**ULID instead of UUIDv7.** The right answer before Postgres 18 and the reason the question was
left open in `CLAUDE.md`. It sorts like UUIDv7 and has a friendlier text form, but it needs an
application library, it has no native Postgres type, and a `text` primary key is wider in every
index — which matters here because ADR-0003 puts `org_id` at the front of every index and those
indexes are on every table. Native beats friendly.

**UUIDv4.** Non-sequential, which satisfies the hard rule, and universally supported. Rejected on
index behaviour: random values scatter inserts across a B-tree, fragmenting pages and inflating
write amplification for no benefit that v7 does not also provide.

**`bigserial`.** Smallest, fastest, and disqualified by the hard rule in `CLAUDE.md` — a customer
who can see `/buildings/7` learns something about the business that we do not intend to publish.

**`numeric` for money.** Correct in the database and the usual recommendation. Rejected because the
correctness stops at the driver boundary: JavaScript has no decimal type, so `numeric` arrives as a
string and every operation on it is an invitation to a float. Integer cents keeps the arithmetic
correct in the language the arithmetic is actually done in.

**Storing money in dollars as a decimal string with a formatting layer.** Same problem, one
indirection further away.

**A single `timestamptz` for every date.** Simplest schema, and it forces every reader to know
which columns have a meaningful time component and which are lying. The install-year case makes it
worst: it would represent a guess as a precise instant.

## Consequences

**What this makes easy.** Ids are opaque, sortable by creation, and generated in one place. Money
arithmetic is integer arithmetic, so the forecast and tax tests assert exact equality rather than
tolerances — which is what makes "the maths gets real unit tests" a meaningful commitment.
Estimated install years are representable as what they are, so the forecast can widen its range for
them (F2) instead of pretending precision it does not have.

**What this makes hard.** Postgres 18 is now a floor, and a managed provider that lags on major
versions is disqualified (#33). Every money value crossing a boundary — JSON, a chart library, a
CSV export (#45) — needs the formatter applied deliberately, and an integer cents value rendered
raw is a bug that looks like a hundredfold error. The four date types mean the schema has to be
read carefully, and `docs/data-model.md` (#9) has to say which is which per column rather than
leaving it to inference.

**Cost of reversal.** Identifiers and money are the two decisions here that are genuinely expensive
after data exists — changing a primary key type rewrites every foreign key and every index in the
database, and changing the money representation touches every stored value and every computation
that reads it. Dates are cheaper, because each column can be migrated independently. This is why
all three are being decided before the first migration rather than after the first bug.
